# Session Notes — 2026-07-07

## Multi-Household Dice: Sequential Flow & Display Fixes

### Summary

Continued multi-household TV dice routing. Moved from simultaneous dice spawning (race conditions, display corruption) to a clean **sequential server flow**. Identified and fixed a critical bug where static display dice crashed the settle/read logic on the defender TV.

---

## Server Changes

### Sequential Dice Flow (AttackWithDice rewrite)

**Before:** Server spawned both attacker and defender dice simultaneously via `PlayerRoll` + `AutoRollBotOpponent`. Both TVs rolled at the same time → race conditions on display, `OnAttackerDiceResult` clearing live defender dice, timing-dependent failures.

**After:** Strict sequential flow:

```
1. Create PendingCombat
2. Send SpawnDice("attacker") to attacker's TV
3. Wait for attacker to submit (10s timeout)
4. Broadcast AttackerDiceResult to all TVs
5. 500ms pause (let clients render static attacker dice)
6. Send SpawnDice("defender") to defender's TV (or RollPrompt if human)
7. Wait for DiceResult (15s timeout — both submitted)
8. Broadcast DefenderDiceResult to all TVs  
9. 500ms pause
10. ResolveCombat → CombatResult → BroadcastState
```

**Benefits:**
- No race conditions — defender TV always has attacker dice placed before defender rolls
- Each TV only processes one event at a time
- Guaranteed event ordering on clients

### PendingCombat — New AttackerSubmitted TCS

Added `TaskCompletionSource<int[]> AttackerSubmitted` — fires when attacker TV calls `SubmitRolledDice("attacker")`. This is the gate between steps 2 and 4.

### Removed AutoRollBotOpponent

Dead code — bot dice spawning is now handled directly in `AttackWithDice` (step 6). Simplified `PlayerRoll` to only handle human defender tap.

### SubmitRolledDice — No Longer Broadcasts

Broadcasts (`AttackerDiceResult`, `DefenderDiceResult`) moved into `AttackWithDice` where timing is controlled. `SubmitRolledDice` now just sets the TCS values.

## Unity Changes

### CombatTheatre — Clean Rewrite

Rewrote event handlers with clear sequential assumptions:

**Attacker TV flow:**
1. `SpawnDice("attacker")` → hard reset, open arena, spawn red dice, physics
2. `SettleAfterDelay` → settle, submit via `SendRolledDice("attacker")`
3. Hold in `ShowingResult` (don't auto-hide — wait for remote blue dice)
4. `OnDefenderDiceResult` → place blue dice statically → `DismissAfterHold(3s)`

**Defender TV flow:**
1. `OnAttackerDiceResult` → hard reset, open arena, place red dice statically
2. `SpawnDice("defender")` → spawn blue dice alongside static red (DON'T clear!)
3. Settle, submit via `SendRolledDice("defender")`
4. `DismissAfterHold(3s)`

**Same-household flow:**
1. `SpawnDice("attacker")` → spawn red, start settle timer
2. `SpawnDice("defender")` → `rollingDefender = true`, spawn blue alongside red
3. Both settle → legacy `SendDiceResult(both)` → `DismissAfterHold(3s)`

Key principles:
- `OnSpawnDice("attacker")` and `OnAttackerDiceResult` are both "new combat" signals → hard reset everything
- `SpawnDice("defender")` NEVER clears dice (attacker dice must remain visible)
- `DismissAfterHold` checks state before acting (avoids stale async tasks interfering)

### DiceRoller — Static vs Active Dice Separation (CRITICAL BUG FIX)

**The bug:** Static dice placed by `PlaceDiceAtValues`/`PlaceDefenderDiceOnly`/`PlaceAttackerDiceOnly` were added to `activeDice`. When `WaitAndReadAll` ran, it tried to call `GetComponent<DiceFaceReader>().ReadTopFace()` on static dice — which have no `DiceFaceReader` → **NullReferenceException** → `WaitSettleAndSend` crashed silently → TV never submitted → 15s server timeout → fallback to server roll.

**The fix:** Two separate lists:
- `activeDice` — physics dice spawned by `SpawnSet` (have `DiceFaceReader`, read on settle)
- `staticDice` — display-only dice placed by `SetupPlacedDie` (no reader, visual only)
- `ClearDice()` destroys both lists
- `WaitForSettle`/`ReadAll` only process `activeDice`

This was the root cause of "defender never submits" in cross-household combat.

## Bug: Bot Attacks Human — No RollPrompt (14:02)

**Symptom:** Bot Bob (scotland) attacks you (england). Bob's dice roll on his arena. You see nothing — no arena, no dice, no Roll button on handset.

**Server log:** `SubmitRolledDice(attacker): [1,4]` appeared at 14:02:47 but no further activity. No `AttackWithDice returned`. 15s later the timeout would have fired.

**Root cause:** `AttackWithDice` throws an exception AFTER the attacker submits (during `AttackerDiceResult` broadcast or `RollPrompt` send). The AI service's catch block swallows the exception with only `Console.WriteLine` (invisible). It then forces through `EndAttack` → `EndTurn` to prevent game freeze.

**Diagnostic added:** `File.AppendAllText("ai-error.log", ...)` in AI catch block — will show full exception + stack trace on next occurrence.

**Likely causes:**
- `hub.Clients.Group(gameCode).SendAsync("AttackerDiceResult", ...)` failing
- `RollPrompt` construction failing (null player name?)  
- Thread context issue after `await AttackerSubmitted.Task` resumes on different thread

## Bug: Previous Working Scenarios Regressing

After fixing the static dice separation (which fixed "you attack bot"), a previously-working scenario broke. The "what was working before" regression suggests the sequential flow has a path-specific issue when the **AI initiates** the attack (vs when the human initiates via `GameHub.Attack`).

Key difference:
- **Human attacks:** `GameHub.Attack` → `AttackWithDice` — hub context is the caller's connection
- **AI attacks:** `AiService.RunTurnAsync` → `AttackWithDice` — hub context is the injected `IHubContext<GameHub>` singleton

Both should work identically, but the exception evidence suggests they don't.

## Debugging Pain Points This Session

1. **`Console.WriteLine` invisible** — doesn't show in app-log or VS Output without specific configuration. Wasted time. Only `ILogger` (app-log) and `Debug.Log` (Unity Console) are reliable.

2. **`System.Diagnostics.Debug.WriteLine` also invisible** — despite running in Debug mode (F5), these never appeared. Reason unclear. Don't use.

3. **AI service swallows exceptions** — `catch (Exception ex) { Console.WriteLine(...) }` means any error in `AttackWithDice` when called by a bot is completely silent. Game continues via recovery path but the real error is hidden. Fixed with file-write diagnostic.

4. **Static dice mixed with physics dice** — the critical bug. `SetupPlacedDie` added display-only dice to `activeDice`, causing `ReadAll()` to crash on null `DiceFaceReader`. Silent NullReferenceException inside an `async Awaitable` — Unity doesn't surface these obviously.

5. **Multiple async tasks running concurrently** — `SettleAfterDelay`, `DismissAfterHold`, `WaitSettleAndSend` all fire-and-forget. If state changes while they're awaiting, they can act on stale assumptions. The clean rewrite added state checks after every await.

6. **Sequential flow eliminates races but creates ordering dependencies** — can't test partial scenarios. If attacker submit fails/delays, the entire flow stalls for the full timeout (10-15s) before fallback.

7. **Two Unity instances with one in editor, one as build** — can only see Debug.Log from the editor instance (Z440). Laptop build errors are invisible without a file-based logging system on that side.
