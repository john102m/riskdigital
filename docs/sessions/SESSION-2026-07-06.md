# Multi-Game Server — Session Notes 2026-07-06

## Status: Working ✅ — Two independent games running simultaneously

## What Was Built

Refactored the server from a single-game singleton to a multi-game architecture. Multiple independent games run concurrently on the same server, each isolated via SignalR groups.

## Pain Points During Implementation

### 1. SignalR doesn't support optional parameters
**Problem:** Changed `RegisterAsTV()` to `RegisterAsTV(string? gameCode = null)`. Unity client called it with zero args — server rejected the invocation before our code ever ran (no logging, just a generic "Failed to invoke" error).

**Solution:** Two separate methods with different names:
- `RegisterTV()` — zero args, auto-detect single game (tv.html backward compat)
- `RegisterAsTV(string gameCode)` — one arg, explicit game code

**Lesson:** SignalR hub methods must have exactly the number of parameters the client sends. No optional params, no overloads.

### 2. Unity connected before game existed
**Problem:** Unity board starts, calls `RegisterTV()`, but no game has been created yet → server threw "No active games".

**Solution:** 
- Made `RegisterTV()` return silently when no games exist (instead of throwing)
- Split the connect flow: connection is established immediately, but game registration is separate
- Poll for available games every 3s until joined
- Final design: Unity shows a join screen, player enters code or picks from list

### 3. GetState called before registration
**Problem:** Original flow called `GetState` before `RegisterAsTV`. After refactoring, `GetState` looks up the game via connection tracking — which isn't set until registration completes.

**Solution:** Registration must happen before `GetState`. Connect flow now: StartAsync → RegisterAsTV(code) → GetState.

### 4. AiService thread safety
**Problem:** AiService was a singleton with instance fields `game` and `gameCode`. Two concurrent games triggering AI would overwrite each other's fields between await points.

**Solution:** `AsyncLocal<T>` — each async call chain gets its own copy. Set at the entry point (`TriggerIfAi`), flows through all awaited methods automatically.

### 5. GameManager code vs GameState code mismatch
**Problem:** `GameManager.CreateGame()` generated a code, but `GameService.CreateGame()` also generated its own internal code. The game was stored under one code but `GameState.GameCode` was different.

**Solution:** Pass the GameManager-generated code into `GameService.CreateGame(... gameCode: code)`.

## Final Architecture

```
Handset ──SignalR──▶ GameHub ──▶ GameManager ──▶ GameService (per game)
                        │                              ▲
Unity TV ──SignalR──────┘                              │
                        │                              │
                   SignalR Groups              AiService (AsyncLocal)
                   (scoped broadcasts)
```

- **GameManager** (singleton) — holds `ConcurrentDictionary<string, GameService>`, tracks connectionId → gameCode
- **GameHub** — routes all calls via `GetCallerGame()` helper, uses `Clients.Group(gameCode)` for all broadcasts
- **GameService** — unchanged logic, no longer a singleton, instantiated per game
- **AiService** (singleton) — receives `game` + `gameCode` per invocation, uses `AsyncLocal` for thread safety

## Resilience Gotchas

### `/admin/reset` (all games)
- Clears GameManager entirely — all games gone, all connection tracking gone
- All connected clients get `GameStateUpdated(null)` 
- Unity boards will show join screen again (no game to be in)
- Handsets return to connect screen
- **Safe** — everyone recovers cleanly

### `/admin/reset/{code}` (single game)
- Removes that game from GameManager
- Players in that game get null state → back to connect screen
- Other games unaffected
- **Gotcha:** Unity board for that game loses tracking — will need to rejoin. Poll won't help because game no longer exists. Board will show join screen if `OnGameStateUpdated` with null triggers the join screen to reappear.
- **TODO:** Make `GameJoinScreen` reappear when state goes null after being joined.

### Unity board disconnect/reconnect
- Reconnect handler calls `RegisterAsTV(joinedGameCode)` → re-joins same game group
- If game was reset during disconnect → RegisterAsTV will throw "Game not found" → board stays on join screen
- **Safe**

### Server restart
- All in-memory state lost (no persistence — by design)
- All clients reconnect via SignalR auto-reconnect
- Unity: RegisterAsTV fails (no games) → shows join screen
- Handsets: Rejoin fails (no games) → shows connect screen
- **Safe** — clean slate

### Multiple games + identical player names
- `Rejoin(playerName)` scans ALL games — first match wins
- If "John" exists in two games, rejoin goes to the first found
- **Low risk** in practice (family game, unique names) but worth noting

## Bugs Found & Fixed During Testing

1. **`GameOverScreen.tsx` called `/admin/reset` (global)** — nuked all games. Fixed to `/admin/reset/{gameCode}`.
2. **SignalR doesn't support optional hub method parameters** — Unity couldn't call `RegisterAsTV(string? gameCode = null)` with zero args. Fixed by splitting into `RegisterTV()` (zero-arg) and `RegisterAsTV(string gameCode)` (one-arg).
3. **Unity `GetState` called before `RegisterAsTV`** — server couldn't find the game. Fixed: register first, then get state.
4. **Unity connect flow not resilient** — `RegisterAsTV` failure killed the whole connect. Fixed: separated connection from registration, swallowed registration errors, poll retries.
