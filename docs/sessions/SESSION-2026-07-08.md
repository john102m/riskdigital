## Root Causes (three separate issues, all fixed)

### Issue 1 — Double broadcast from `SubmitDiceResult` (GameHub.cs)

When multi-household support was added, `SubmitDiceResult` in `GameHub.cs` was given
extra broadcasts for `AttackerDiceResult` and `DefenderDiceResult` to serve spectator
TVs. But `AttackWithDice` already broadcasts both those events after resolving —
with the correct `{values, sourceId, targetId}` payload shape.

Result: double broadcast. The first (from `SubmitDiceResult`) sent a plain `int[]`.
The Unity `SignalRClient` handler for `AttackerDiceResult` expects a `JsonElement`
with `.values`/`.sourceId`/`.targetId` — it crashed silently on a plain array.
The second broadcast (from `AttackWithDice`) arrived after the arena state machine
had moved on, causing the panel to re-open showing only defender dice.

**Fix:** Removed the three broadcast lines from `SubmitDiceResult` in `GameHub.cs`.
`AttackWithDice` handles all broadcasts — correct shape, correct timing.

### Issue 2 — Inspector values on `SignalRClient` not cleared at join time

`SignalRClient` had `householdId = "Household"` and `playerIndices = [0]` serialized
into the scene from previous multi-household testing. `ApplyHouseholdConfig` in
`GameJoinScreen` only wrote to these fields when valid household input was provided —
it never cleared them when input was blank/invalid.

With `householdId` set and `playerIndices = [0]`, `IsMyPlayer(botIndex)` returned
`false` for any bot player not in the list. So `SpawnDice("defender")` was treated
as cross-household — TV submitted only attacker dice via `SubmitRolledDice("attacker")`
instead of the combined `SubmitDiceResult`. Server waited 15s for a defender
submission that never came.

**Fix:** `ApplyHouseholdConfig` now always writes to `signalR.householdId` and
`signalR.playerIndices` — either the parsed values if valid input provided, or
empty/cleared if not. Inspector defaults can no longer survive a join.

### Issue 3 — TMP_InputField text area had "Household" baked in as real text

The household `TMP_InputField` in the scene had "Household" set as actual text
content (not just placeholder), saved into the scene/prefab. This persisted through
editor saves and scene reloads. `householdInput.text` always returned "Household".

`ApplyHouseholdConfig` checked for a space+digits pattern before applying config,
so "Household" (no space, no indices) was correctly rejected — but since the clear
path wasn't previously in place, the stale Inspector values were left untouched.
Fixed by Issue 2's change (explicit clear on invalid input).

Additional defensive fix: known placeholder strings ("Household", "Household name")
are explicitly stripped to empty before validation, so even if the text area content
changes wording it won't accidentally be treated as household config.

## Key Lesson

`ApplyHouseholdConfig` must always write to `signalR.householdId`/`playerIndices`,
not just when valid input is present. Any early-return on invalid input leaves
stale serialized Inspector values in place. Pattern: **always write, never silently skip**.

---

## Note — Household Input is Temporary Scaffolding

The "england 0,2" text input for household config is a dev/test mechanism only.
In production, household assignment needs a proper UX — lobby picker, QR code,
or auto-detection by IP. The explicit placeholder string strip (`"Household"` etc.)
is a hack to work around a baked-in scene value, and can be removed when the
input field is replaced with a real selection mechanism.
